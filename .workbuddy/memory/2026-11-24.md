## 共用组件按方案切换 Link（修复 ice SSR 降级 CSR）

- 问题：`src/components/AppNaviagtor/index.tsx` 直接 `import { Link } from 'react-router-dom'`，ice 预渲染时拿不到 Router context，报 `Cannot destructure property 'basename' of useContext(...) as null` 并降级 CSR（只影响 ice 方案；webpack 方案有 BrowserRouter/StaticRouter 包裹，正常）。
- 关键事实：`@ice/runtime/esm/index.d.ts` 里 `export { Link, ... } from 'react-router-dom'`——ice 的 Link 就是 react-router-dom 的 re-export，但从 `ice` 虚拟模块导入才与 ice runtime 的 Router context 同源。只有一份 react-router-dom@6.21.3，问题不是版本而是 context 实例。
- 方案：组件统一写 `import { Link } from 'ice'`；ice 构建用它自己的虚拟模块（已验证预渲染报错消失、三个 HTML 含真实内容）；webpack 方案新增 `src/ice-link-shim.ts`（`export { Link } from 'react-router-dom'`），`webpack.config.js` 的 resolve.alias 加 `'ice$': path.join(srcDir, 'ice-link-shim.ts')`（`$` 精确匹配）。
- 验证：两套 build 均 exit 0、ice 无 basename/降级日志；dist/js/main.js 里 Link 正常解析到 react-router-dom；egg 读 dist 三路由 200、SSR 输出 `<a href="/home">` 正确；headless Chrome 点击 Home 链接 URL 变 `/home` 且 `window.__spaMarker` 保持（SPA 跳转非整页刷新）、hydrate 无 console error。

## webpack + egg SSR 支持流式响应（2026-11-24 傍晚）

- 需求：SSR 用 React 18 `renderToPipeableStream` 流式输出，异步边界就绪前先发首屏 shell。
- 关键事实：React `pipe(dest)` 会 end 掉目标流 → 不能直接 pipe 到 res 再补文档尾。
- 实现（三层）：
  - `src/entry-server.tsx`：新增 `renderToStream(req, opts)` → `{statusCode, headers, stream, done, abort}`。两层 PassThrough：React pipe 进 reactPass，其 data 同时收集到 reactHtml 并写入 output；reactPass end 时 output.end(文档尾) + resolveDone 完整 HTML。head 先写 output；bootstrap script 由 React `bootstrapScripts` 注入（模板不再写 main.js script）；dev 脚本文本走 `bootstrapScriptContent`。保留 `renderToHTML` 供缓存后台刷新/404。
  - `server/app/service/ssr.js`：MISS/BYPASS 走 `doRenderStream`，`result.done.then(html => cache.set(...))` 写缓存；HIT/STALE 仍整串。流式 Readable 不能跨请求共享 → 流式 MISS 不走 singleflight（取舍已写入 README）。
  - `server/app/controller/home.js`：有 stream 则 `ctx.respond=false`，设完 status/headers 后 `stream.pipe(ctx.res)`，res close 时 abort，流 error 时未发头回 500/已发头销毁。
  - `config.ssr.stream`（默认 true）开关；`app.js` 校验 renderToStream 导出；`dev-hot-reload.js` 抽出纯脚本文本 `devScript` 供流式注入。
- 坑：第一版漏了 `reactPass.on('data')` 里 `output.write(c)`，导致 stream 只有 head+tail、done 却完整——data 收集与转发必须同时做。
- 验证：TTFB 7ms vs 完整 508ms（500ms Suspense 延迟），4 块（7/7/507/507ms，含 fallback 与最终内容）；MISS 无 content-length、HIT 有 content-length 1209；BYPASS chunked；404/静态资源正常；headless Chrome hydrate 点击计数 1→2、marker kept、无 console error；dev 下 EventSource 脚本注入 1 次；dev 热更新在流式路径仍生效。临时延迟组件已移除并重建。

## /ug 常驻 3s 流式演示边界（2026-11-24 晚）

- 需求：在 `src/pages/ug/index.tsx` 加一个 3s 后才渲染内容的边界，方便直接观察流式响应。
- 实现：新增 `src/ug-delay.ts` 管理延迟状态；`entry-server.tsx` 在两个渲染入口开头调 `beginDelayRequest(streaming)`（流式 true、非流式 false，onShellError 降级前也调 false），`ug/index.tsx` 的 `DelayedContent` 调 `suspendForDelay()`，首次渲染抛出 3s Promise，外层 Suspense fallback 为「loading...（3 秒后显示内容）」。
- 关键点：最初把「3s 后自动重置 state」写在组件模块里，结果重置抢在 React 边界重试前，导致不断重新挂起、流永不结束。改成按请求在渲染入口显式 `beginDelayRequest()` 重置后正常。客户端 `typeof window !== 'undefined'` 直接返回、不延迟，避免 hydrate 不一致。
- 验证：chunk 时间 1/6/3007/3010ms；HTTP 连续两次请求 TTFB 4ms/2ms、完整 3009ms/3004ms 且都含 fallback 与内容；非流式 renderToHTML({req:{url:'/ug'}}) 3ms 出完整内容；headless Chrome 1s 见 fallback、4s 见内容、点击计数 1→2、无 console error；ice build 仍 exit 0 且 ug.html 有预渲染内容。README 已加观察说明与目录树条目。
